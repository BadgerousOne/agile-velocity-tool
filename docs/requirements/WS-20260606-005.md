# Requirements — WS-20260606-005
# Persist Agent Buddy Conversation History Across Page Reloads

**Status:** Approved
**Author:** Solution Lead
**Date:** 2026-06-06
**GitHub Issue:** #4

---

## Problem

Agent Buddy holds conversation history in React `useState`. That state is destroyed on every page reload or Electron window restart. Users must repeat context, re-explain their questions, and re-trigger health chips on every session. The experience is stateless by accident, not by design.

---

## Goals

1. Conversation history survives page reloads and Electron restarts.
2. History is scoped to the active workspace — switching workspaces loads that workspace's history.
3. Users can explicitly clear the persisted history.
4. Storage overhead is bounded — a stale multi-day conversation cannot silently bloat localStorage.

## Non-Goals

- Cloud sync or cross-device persistence.
- Persisting Ollama connectivity state (`ollamaOnline`, `toolsEnabled`) — these are re-probed on open.
- Persisting pending sprint proposals — a pending `CREATE_SPRINT` action from a prior session is meaningless because the user is gone and cannot confirm it.
- Exporting or importing history — out of scope for this workstream.

---

## Functional Requirements

### FR-1 — Load persisted history on mount

On component mount, read persisted messages from localStorage for the active workspace. Assign fresh in-memory IDs. Treat any message with `action.status === 'pending'` as `'cancelled'` (the proposal is stale).

### FR-2 — Persist messages on every change

After every update to the `messages` array, write the serialized history to localStorage. Persist only the fields needed for display: `role`, `content`, `chips`, `action` (type + data + status). Do not persist `id` (re-assigned on restore) or `error` flag (ephemeral).

### FR-3 — Storage key scoped per workspace

Storage key: `buddy_history_ws-${activeWorkspaceId}`

The default workspace uses `activeWorkspaceId = null` or the default key; the key must remain stable for the default workspace across sessions.

### FR-4 — Storage cap

Cap at **100 messages** or **256 KB** (raw JSON string length), whichever limit is hit first. When the cap is hit, drop the oldest messages from the head of the array. Apply the cap before writing, not before reading.

### FR-5 — Workspace switch loads the incoming workspace's history

When `activeWorkspaceId` changes, replace messages with the persisted history for the new workspace (or an empty array if none). Do not show the first-run welcome message again if history already exists for that workspace.

### FR-6 — Clear history control

Add a "Clear" button to the Buddy panel header. Clicking it:
1. Sets `messages` to `[]` (triggering FR-2, which writes `[]` to localStorage).
2. Resets the `buddy_first_opened` flag for the current workspace so the welcome message re-appears.

### FR-7 — First-run message not duplicated

The welcome message (chips) is shown only when there is no persisted history for the current workspace. It must not be stored in localStorage (it is ephemeral and regenerated if needed).

---

## Non-Functional Requirements

### NFR-1 — No startup latency regression

localStorage reads are synchronous. The lazy `useState` initializer (already used in the component) is the correct integration point — no async loading, no flash of empty state.

### NFR-2 — Existing Buddy features unaffected

- Ollama status detection (IPC + HTTP probe) — unchanged
- Tool-call path (T3.5) and fence-parse path (T3.1) — unchanged
- Sprint preview / confirm / cancel flow — unchanged; only the confirmed/cancelled terminal states are stored
- Health alert cards — not stored (derived from sprint data, not conversation)

### NFR-3 — No new dependencies

Pure localStorage + existing React patterns. No new libraries.

---

## Storage Key Reference

| Key | Content |
|-----|---------|
| `buddy_history_ws-${activeWorkspaceId}` | JSON array of serialized messages for that workspace |
| `buddy_first_opened` | Existing flag — will be scoped per workspace in implementation (see FR-7 note) |

> Note: `buddy_first_opened` is currently a single global flag. Implementation should not change its semantics beyond what is required for FR-7. Scoping it per workspace is acceptable but not required.

---

## Acceptance Criteria

- [ ] Messages persist across a hard page reload (Ctrl+R / cmd+R)
- [ ] Messages persist across Electron window close and reopen
- [ ] Switching workspaces shows the correct history for each workspace
- [ ] Clearing history removes messages from the UI and from localStorage
- [ ] After clearing, the welcome chip message reappears on next open
- [ ] A pending sprint proposal from a prior session is rendered as cancelled, not pending
- [ ] Storage is capped: a 200-message conversation stores only the last 100 messages
- [ ] No regression in Ollama probe, tool calls, sprint creation, or health alerts
