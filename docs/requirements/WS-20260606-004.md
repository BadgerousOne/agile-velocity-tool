# Requirements — WS-20260606-004
# Align Ollama URL config between Electron main and Settings UI

**Role:** Solution Lead
**Status:** Approved
**Completed:** 2026-06-06
**Workstream:** WS-20260606-004
**GitHub Issue:** #3

---

## Problem Statement

Two URL misalignments exist between the Electron main process and the renderer:

**Misalignment 1 — watchdog vs. user-configured URL:**
`electron/ollama.js` hard-codes `http://127.0.0.1:11434` in `probePort()`. If a user sets a custom Ollama URL in Settings (stored in `localStorage` as `buddy_ollama_url`), the renderer's Buddy panel correctly uses it — but the main process watchdog still probes the default port. On a non-default port, the watchdog sees "no response" and attempts a restart of the bundled binary, which is wrong.

**Misalignment 2 — CSP vs. renderer default URL:**
The production CSP (`electron/main.js`) allows `http://127.0.0.1:11434`. The renderer defaults to `http://localhost:11434` (`AgentBuddy.jsx` line 10, `Settings.jsx` line 95). These are different origins — in production, all renderer Ollama API calls using the default URL are blocked by the CSP.

---

## Goals

1. The Electron main process watchdog uses the user-configured Ollama URL (not a hard-coded constant)
2. The production CSP allows the renderer's default Ollama URL (`localhost:11434`) in addition to the existing `127.0.0.1:11434`
3. The URL is communicated from renderer to main via IPC on every app launch — no filesystem reads needed

---

## Non-Goals

- Dynamic CSP update when the user changes the URL mid-session (complex; out of scope)
- Supporting non-localhost Ollama URLs in the CSP (security risk; out of scope)
- Storing the Ollama URL outside of localStorage (out of scope)

---

## Functional Requirements

### FR-001 — IPC bridge for URL
- `electron/preload.js` exposes `window.ollamaApi.setUrl(url)` via `ipcRenderer.invoke('ollama:setUrl', url)`
- `electron/main.js` registers `ipcMain.handle('ollama:setUrl', ...)` and forwards to `ollama.js`
- `electron/ollama.js` exports `setOllamaUrl(url)` which updates a module-level variable used by `probePort()`

### FR-002 — Renderer sends URL on mount
- `src/App.jsx` calls `window.ollamaApi?.setUrl(url)` in a `useEffect` on mount, reading `buddy_ollama_url` from localStorage (defaulting to `http://localhost:11434`)
- The `?.` guard ensures this is a no-op in browser mode (where `window.ollamaApi` is undefined)

### FR-003 — CSP fix
- Add `http://localhost:11434` to the `connect-src` directive alongside the existing `http://127.0.0.1:11434`
- No other CSP changes

### FR-004 — Backward compatibility
- Default behavior is unchanged: if no custom URL is set, both the renderer and the watchdog use `http://localhost:11434` (renderer) / `http://127.0.0.1:11434` (watchdog) — after this fix, the watchdog will also use `localhost:11434` as its default to stay consistent
- Existing `window.ollamaApi.onStatus` / `offStatus` surface is unchanged

---

## Non-Functional Requirements

- NFR-001: No new npm dependencies
- NFR-002: `npm run test:run` remains green
- NFR-003: Change is invisible to the user — no new UI

## Open Questions (resolved)

| Question | Resolution |
|---|---|
| Where does the renderer send the URL on startup? | `App.jsx` useEffect — always mounts, regardless of active tab or buddy state |
| Should we use `invoke` or `send` for IPC? | `invoke` (request/reply) — cleaner than fire-and-forget for a config setter |
| Default URL alignment: should watchdog default match renderer default? | Yes — change watchdog default from `127.0.0.1` to `localhost` so they agree out of the box |
